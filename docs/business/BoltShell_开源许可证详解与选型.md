# BoltShell 开源许可证详解与选型

> 更新：2026-08-21
> 关联文档：[商业化与开源策略](BoltShell_商业化与开源策略.md) · [竞品变现与广告风险调研](BoltShell_竞品变现与广告风险调研.md) · [客户端赞助数据统计设计](BoltShell_客户端赞助数据统计设计.md) · [文档索引](../README.md)
> 用途：把 MIT / Apache / GPL / BSL / ELv2 等许可证讲清楚，并回答「BoltShell 到底开不开源、开哪部分、用什么许可证」。

## 一、结论先看

| 问题 | 答案 |
|------|------|
| 许可证能不能防止别人 fork 去广告、去 License 校验？ | **不能**。MIT、Apache-2.0、GPL 全都不能 |
| Apache-2.0 唯一能挡住的是什么？ | **名字**。§6 明确不授予商标权 → fork 必须改名，不能叫 BoltShell |
| 真正能防「fork 去广告版」的手段？ | 只有三条：① **不开源**那部分代码 ② 用 **source-available 许可**（ELv2 / BSL）③ 商标 |
| GPL 能防吗？ | 反而更糟。GPL 只强制对方也开源，**不禁止**去广告、也不禁止商用分发 |
| BoltShell 当前 LICENSE | Apache-2.0（已存在，方向正确） |
| 推荐方案 | **方案 B：WindTerm 式部分开源**（详见 §六），Apache-2.0 覆盖已开源部分 |
| 我们的技术栈有 copyleft 传染风险吗？ | **基本没有**。Go 的 `x/crypto/ssh` 是 BSD-3，Wails / Vue / xterm.js 都是 MIT（详见 §七） |

**一句话：** 选许可证是在决定「别人能拿走什么」，而不是「别人不能干什么」。想保住 Pro，靠的是**不开源关键代码 + 商标**，不是挑一个更严的开源许可证。

---

## 二、先分清三大类

| 类别 | 核心逻辑 | 代表 | 是否 OSI 认可的「开源」 |
|------|----------|------|------------------------|
| **宽松型**（Permissive） | 随便用，保留声明就行；**允许闭源二次分发** | MIT、BSD、Apache-2.0 | ✅ 是 |
| **传染型**（Copyleft） | 你用了我，你的衍生也必须同样开源 | GPL、AGPL、LGPL、MPL | ✅ 是 |
| **源码可见型**（Source-available） | 代码公开可读，但**加了商业限制** | BSL 1.1、Elastic License 2.0、SSPL、FSL | ❌ **不是开源** |

第三类最容易误用。它们的代码在 GitHub 上能看、能改、能自用，但**不能对外宣称「开源」**——OSI 不认可，社区会公开纠正，某些 Linux 发行版和包管理器也不会收录。用词必须诚实：叫 **source-available** 或 **商业友好可见源码**。

## 三、宽松型许可证详解

### 3.1 MIT

| 项目 | 内容 |
|------|------|
| **一句话** | 最短最宽松，全文不到 200 词 |
| **你必须做** | 在副本和实质性部分中保留版权声明与许可声明 |
| **别人能做** | 用、改、卖、闭源分发、改名（许可证本身不管商标） |
| **专利** | ❌ **无专利授权条款**（潜在风险：贡献者日后拿专利来告你，法理上没有明文豁免） |
| **商标** | 未提及 |
| **谁在用** | Tabby、electerm、Wails、Vue、xterm.js |

**对 BoltShell 的含义：** MIT 是「最容易被白嫖」的选择。Tabby 和 electerm 用它，代价就是我们调研到的那个结果——完全没有商业护城河，收入只能靠自愿赞助（每月 $35～400 档）。

### 3.2 BSD-2-Clause / BSD-3-Clause

| 项目 | 内容 |
|------|------|
| **一句话** | 和 MIT 几乎等价 |
| **BSD-3 多的那一条** | **非背书条款**：不得用原作者或组织的名义为衍生产品做背书宣传 |
| **专利** | ❌ 无明文专利授权 |
| **谁在用** | Go 标准库、`golang.org/x/*`（含 `x/crypto/ssh`） |

**对 BoltShell 的含义：** 我们的 SSH 实现依赖 `golang.org/x/crypto/ssh`，它是 BSD-3。这意味着**我们的 SSH 核心可以完全闭源**——这是比 WindTerm 更有利的位置（见 §7.2）。

### 3.3 Apache-2.0 ⭐（BoltShell 当前使用）

这是宽松型里条款最完整的一个，四个关键条款必须搞清：

| 条款 | 内容 | 对我们的意义 |
|------|------|-------------|
| **§3 专利授权** | 贡献者显式授予专利许可；若有人拿专利起诉本项目，其许可自动终止 | 比 MIT 安全，企业用户法务更容易过审 |
| **§4(b) 修改声明** | 修改过的文件必须**显著标注「你改过」** | fork 者不能假装是原版 |
| **§4(d) NOTICE 文件** | 若原项目带 `NOTICE`，衍生必须保留其中的归属声明 | 可以把「基于 BoltShell」写进 NOTICE，fork 者必须保留 |
| **§6 商标** | **明确不授予**商标、商号、产品名、服务标记的使用权 | ⭐ **这是我们唯一的有效武器**：fork 可以存在，但不能叫 BoltShell |

**别人拿到 Apache-2.0 的 BoltShell Community 后，合法可以做的事：**

- ✅ 删掉赞助位代码，编译一个「无广告版」
- ✅ 把 `LicenseChecker.IsPro()` 改成永远返回 `true`
- ✅ 打包分发、甚至收费卖
- ✅ 闭源自己的修改
- ❌ 继续叫「BoltShell」或用我们的 Logo（§6 + 商标法）
- ❌ 声称得到我们的背书

**所以文档里那句「Fork 需改名」是有法律依据的**，但「Fork 不能去广告」**没有**依据。这是选型时最容易搞错的一点。

### 3.4 三者对比

| | MIT | BSD-3 | Apache-2.0 |
|---|---|---|---|
| 篇幅 | 极短 | 短 | 长（约 10 页） |
| 专利授权 | ❌ | ❌ | ✅ |
| 修改需声明 | ❌ | ❌ | ✅ |
| 商标明确排除 | ❌ | 部分（非背书） | ✅ |
| 企业法务友好度 | 中 | 中 | **高** |
| **推荐给 BoltShell** | — | — | ✅ **保持不变** |

## 四、传染型（Copyleft）许可证详解

### 4.1 传染强度阶梯

```
MPL-2.0  <  LGPL-3.0  <  GPL-3.0  <  AGPL-3.0
文件级      库级         整个程序     连 SaaS 也算
```

### 4.2 MPL-2.0（Mozilla）

| 项目 | 内容 |
|------|------|
| **传染范围** | **文件级**。只有你改动的 MPL 文件必须开源，同一程序里的其他文件可闭源 |
| **能否与闭源共存** | ✅ 可以（§3.3「Larger Work」条款） |
| **对 BoltShell** | 是「想开源又想留闭源模块」的温和选择，但生态里不常见，社区认知成本高 |

### 4.3 LGPL-2.1 / 3.0

| 项目 | 内容 |
|------|------|
| **传染范围** | **库级**。动态链接调用 LGPL 库时，你的主程序可以闭源；但必须允许用户**替换/重新链接**该库 |
| **静态链接** | 麻烦得多，需要提供目标文件或源码以支持重新链接 |
| **典型代表** | **libssh**（LGPL-2.1） |
| **对 BoltShell** | ⭐ 关键：**这解释了 WindTerm 为什么必须开源它的 libssh 改版**。WindTerm README 里那句「as well as all types that require open source according to the license」指的就是这个——不是它想开源，是 LGPL 逼它开源。我们用 Go 的 `x/crypto/ssh`（BSD-3），**没有这个义务** |

### 4.4 GPL-2.0 / 3.0

| 项目 | 内容 |
|------|------|
| **传染范围** | **整个程序**。任何链接、集成 GPL 代码的作品，分发时必须整体以 GPL 开源 |
| **GPL-3.0 额外条款** | 反 Tivo 化（消费级设备必须允许安装修改版）、明确专利授权、防数字锁 |
| **对我们最要命的** | **不能有闭源 Pro 模块**。Open Core 模式与 GPL 直接冲突 |
| **注意：它防不住 fork 去广告** | GPL 只要求对方也开源。别人完全可以合法地做一个「GPL 的、去广告的、免费的 BoltShell 分支」——**比 Apache 的情况对我们更糟**，因为它还能吸引其他人一起维护那个分支 |
| **典型代表** | WinSCP（GPLv3）、FileZilla、Termux |

### 4.5 AGPL-3.0

| 项目 | 内容 |
|------|------|
| **比 GPL 多什么** | **§13 网络条款**：用户通过网络与程序交互，也必须能拿到源码 |
| **用途** | 防云厂商白嫖 SaaS（Grafana、MongoDB 早期思路） |
| **对 BoltShell** | ❌ 不适用。我们是桌面客户端，主要威胁不是「云厂商拿去做托管服务」，而是「个人 fork 去广告」。AGPL 解决不了后者 |

## 五、Source-available（不是开源，但对我们最相关）

这一类是 2019 年后商业开源公司的主流选择，专门解决「开源了却赚不到钱」。

### 5.1 BSL 1.1（Business Source License，MariaDB 提出）

| 要素 | 说明 |
|------|------|
| **机制** | 代码公开，但作者可加**附加使用授权**（Additional Use Grant）限制商业用途 |
| **Change Date** | 到期后（最长 4 年）**自动转为**指定的开源许可（通常 Apache-2.0 或 GPL） |
| **典型限制写法** | 「除非另行购买商业授权，不得将本软件作为竞争性托管服务提供给第三方」 |
| **谁在用** | MariaDB MaxScale、CockroachDB、Sentry（后转 FSL）、HashiCorp Terraform（1.6 起）|
| **对 BoltShell** | 可用于 **Pro 模块** 的源码公开而不失控。但社区争议大，HashiCorp 换 BSL 后直接引发 OpenTofu 分叉 |

### 5.2 Elastic License 2.0（ELv2）⭐ 值得细看

只有三条限制，**其中第二条正是我们担心的事**：

| # | 限制 | 对 BoltShell 的意义 |
|---|------|--------------------|
| 1 | 不得将软件作为**托管或管理服务**提供给第三方 | 对桌面客户端不太相关 |
| 2 | **不得规避许可密钥功能，不得移除或隐藏受许可保护的功能** | ⭐ **直接禁止「改掉 `IsPro()` 返回 true」和「删掉赞助位」** |
| 3 | 不得移除或混淆作者的版权与其他声明 | 保护品牌归属 |

**这是唯一一个在许可条款层面明文禁止「fork 去广告 / 破解 Pro」的常见许可证。** 代价：

- ❌ 不是 OSI 开源，**不能宣称「开源」**，只能说「源码公开」
- ❌ 会被一部分社区抵制，GitHub 的 star 增长会受影响
- ❌ 可能进不了 Homebrew core、某些 Linux 发行版仓库
- ⚠️ 与「Community 版 Apache-2.0 建立信任」的叙事冲突

### 5.3 FSL（Functional Source License，Sentry 提出）

| 要素 | 说明 |
|------|------|
| **机制** | BSL 的简化版：禁止竞争性使用，**2 年后**自动转为 MIT 或 Apache-2.0 |
| **优点** | 转换期比 BSL 的 4 年短，社区接受度稍好 |
| **对 BoltShell** | 桌面工具迭代快，2 年前的版本转开源基本无害，是比 BSL 更温和的选项 |

### 5.4 SSPL（MongoDB）

提供服务者必须开源**整个服务栈**（含管理工具、备份、编排）。OSI 明确拒绝认定为开源，业界评价负面。**BoltShell 不要用。**

## 六、核心结论：许可证防得住什么，防不住什么

### 6.1 威胁 × 许可证 对照表

| 我们担心的行为 | MIT | Apache-2.0 | GPL-3.0 | ELv2 / BSL | 不开源 |
|----------------|-----|------------|---------|------------|--------|
| 删掉赞助位重新编译 | ❌ 防不住 | ❌ 防不住 | ❌ 防不住 | ✅ 条款禁止 | ✅ 拿不到代码 |
| 改 `IsPro()` 破解 Pro | ❌ | ❌ | ❌ | ✅ 条款禁止 | ⚠️ 仍可逆向二进制 |
| 打包分发甚至收费卖 | ❌ | ❌ | ❌（须同样开源） | ✅ | ✅ |
| 竞品抄 UI 与交互 | ❌ | ❌ | ❌ | ⚠️ 部分 | ⚠️ 看得见就能抄 |
| **继续叫「BoltShell」** | ⚠️ 靠商标法 | ✅ **§6 明确排除** | ⚠️ | ✅ | ✅ |
| 假装是官方原版 | ❌ | ✅ §4(b) 须标注修改 | ✅ | ✅ | ✅ |

**读法：** 除了「名字」和「须标注修改」，开源许可证在商业保护上**基本无能**。这不是选错了许可证，而是开源的定义本身如此。

### 6.2 三个候选方案

#### 方案 A：全部 Apache-2.0 开源（Tabby / electerm 路线）

| | |
|---|---|
| 做法 | 客户端全部代码开源，Pro 只是 feature flag |
| 优点 | 社区信任最高、star 增长最快、贡献者最多 |
| 缺点 | **Pro 等于卖良心**。一行代码就能破解，去广告版会在几天内出现 |
| 收入现实 | 参考 electerm（Sponsors 目标 $100/月）、Tabby（OpenCollective 余额数百美元） |
| 适合 | 把 BoltShell 当作品和个人品牌，不指望它赚钱 |

#### 方案 B：WindTerm 式部分开源 ⭐ 推荐

| | |
|---|---|
| 做法 | **开源**：终端渲染、SFTP、监控、连接管理 UI、加密与凭据保护、工具库<br>**闭源**：License 校验、赞助位配置下发、Pro 功能模块、云同步 |
| 许可证 | 已开源部分用 **Apache-2.0**；README 明确写「partial open source」 |
| 优点 | 拿到开源的信任与 star，同时 Pro 不是一行 flag 能破的；**先例明确**（WindTerm 就这么活着） |
| 缺点 | 会被少数人批「假开源」；需要维护两套构建（开源包 / Pro 包） |
| 关键前提 | **必须诚实标注**。WindTerm 的做法是在 README 第一行就写明 partial，不藏 |
| 对我们额外有利 | 我们用 `x/crypto/ssh`（BSD-3），**没有 LGPL 义务**，闭源自由度比 WindTerm 还高 |

#### 方案 C：客户端 source-available（ELv2）

| | |
|---|---|
| 做法 | 全部代码公开，但用 ELv2 禁止「移除赞助位 / 规避许可密钥」 |
| 优点 | 唯一在**条款层面**禁止破解与去广告的方案 |
| 缺点 | **不能说自己开源**；与「开源建立信任」叙事冲突；对个人开发者，维权基本只能靠 DMCA 下架，实际执行力有限 |
| 适合 | 已经有一定用户量、且确认 Pro 是主要收入之后 |

### 6.3 「是否开源」的决策框架

不要问「要不要开源」，问这四个问题：

| 问题 | 如果答案是 A | 如果答案是 B |
|------|-------------|-------------|
| **1. BoltShell 对你是作品还是生意？** | 作品 → 方案 A，别纠结了，全开源，享受 star | 生意 → 方案 B/C |
| **2. Pro 的杀手功能，是「关掉一个开关」还是「一堆真代码」？** | 开关（去广告 / 解除连接数上限）→ **开源就等于放弃 Pro** | 真代码（云同步、审计、Snippets 引擎）→ 开源主体无害，闭源那几个模块即可 |
| **3. 你能承受「一周内出现去广告 fork」吗？** | 不能 → 方案 B | 能（认为大部分用户不会去找 fork）→ 方案 A |
| **4. 你更怕失去哪一个：社区信任，还是收入？** | 信任 → A | 收入 → B |

**按现有规划推断：** 商业化文档把「去除广告 / 赞助位」和「无限连接数」列为 Pro 前两个卖点——这两个都是**开关型**，问题 2 的答案是 A。所以如果走方案 A 全开源，Pro 基本无法成立。

**这直接指向方案 B**，并且顺带给出一个结论：**Pro 的功能清单需要往「真代码」倾斜**（Snippets 引擎、会话录制、配置导入、云同步），把「去广告」降级为附带福利而不是主卖点。这也和「取消 Pro 去广告、赞助位全员可见」的想法方向一致。

## 七、依赖许可与合规注意

### 7.1 我们技术栈的许可分布

| 依赖 | 许可证 | 传染性 | 备注 |
|------|--------|--------|------|
| Go 标准库 | BSD-3 | 无 | |
| `golang.org/x/crypto/ssh` | BSD-3 | 无 | ⭐ SSH 核心可闭源 |
| Wails | MIT | 无 | |
| Vue 3 / Element Plus | MIT | 无 | |
| xterm.js | MIT | 无 | |
| SQLite | Public Domain | 无 | |

**结论：整条链路没有 copyleft 传染，闭源 Pro 模块在法律上完全可行。**

### 7.2 需要主动避开的坑

| 坑 | 说明 |
|----|------|
| **误引入 LGPL/GPL 库** | 例如换用 C 的 `libssh`（LGPL）或某些 GPL 的终端组件，会立刻产生开源义务。**引入新依赖前先看许可证** |
| **字体** | JetBrains Mono / Fira Code / Cascadia Code 多为 **OFL-1.1**：可随软件分发，但**改动后不得沿用保留字体名**（Reserved Font Name） |
| **图标** | Font Awesome 免费版图标是 CC-BY-4.0（需署名）；Lucide 是 ISC；Element Plus Icons 是 MIT。**混用前逐个确认** |
| **配色方案 / 主题** | 从其他终端移植的配色可能带许可，注明来源 |
| **NOTICE 文件** | Apache-2.0 项目若带 NOTICE，我们必须保留其内容；我们自己也应建一个 `NOTICE`，把「BoltShell」归属写进去，让 fork 者必须保留 |
| **第三方许可清单** | 发版时随包提供 `THIRD_PARTY_LICENSES.txt`，Go 可用 `go-licenses` 生成 |

### 7.3 文档、Logo 与品牌不要用开源许可

| 资产 | 建议 |
|------|------|
| 源代码 | Apache-2.0（已开源部分） |
| `docs/` 文档 | CC-BY-4.0 或「保留所有权利」；**不要**放进代码许可范围 |
| Logo / 图标 / 名称 | **保留所有权利 + 商标**。绝不能用 Apache-2.0 覆盖，否则 fork 者可以合法用我们的 Logo |
| 官网素材 | 同上 |

README 里建议明确写一段 **商标政策**：

> BoltShell 名称与 Logo 为商标，不在 Apache-2.0 授权范围内（见许可证 §6）。
> Fork 或衍生发行版**必须改用其他名称与图标**，且不得暗示获得官方背书。
